# ClipDock — Project Map

## [TECH_STACK]

- **Target:** Windows 10/11 x64.
- **Runtime:** CPython 3.10–3.14; development interpreter currently CPython 3.14.7.
- **GUI:** PySide6 `6.11.2` (Qt 6, LGPL distribution route; license notices must ship with packaged builds).
- **Extraction:** yt-dlp `2026.8.19` (PyPI wheel; Unlicense for the Python package).
- **Media processing:** FFmpeg `9.0.2` Windows x64 LGPL build, supplied under `vendor/ffmpeg/`; the application never shells out for metadata and invokes yt-dlp's post-processors for merge/remux/transcode.
- **Packaging inputs:** pinned `requirements.txt`; `tools/fetch_dependencies.py` downloads the pinned yt-dlp executable and FFmpeg archive with SHA-256 verification. No new runtime dependency is permitted without approval.
- **Executable packaging:** PyInstaller is a **build-time-only** tool installed on demand by `scripts/build_exe.ps1`; it is intentionally excluded from `requirements.txt` so the approved runtime dependency set stays PySide6 + yt-dlp.
- **Test stack:** Python standard-library `unittest`, mocks, and local generated media fixtures; no test-only third-party dependency.
- **Logging:** standard-library `QueueHandler`/`QueueListener` with a rotating UTF-8 file handler.

## [SYSTEM_FLOW]

1. User enters one YouTube video URL, explicitly selects **Playlist** and enters a YouTube playlist URL, or selects **Batch queue** and enters any number of links, then selects an output directory. The upper-right **Theme** badge and selector switch between 12 explicit, high-contrast palettes without interrupting work; the control is sized to fit the longest name in its own list and keeps that width at every window size, including maximized and full-screen.
2. User presses **Fetch details** for the single-video and playlist modes; the batch queue reads each of its own links and needs no fetch step. The UI worker normalizes/validates the host and URL mode, calls yt-dlp without downloading, and returns either single-video metadata or playlist metadata. Single-video modes reject collection links; playlist mode also accepts a `watch?v=...&list=...` link and reduces it to its playlist, reads entries, keeps un-downloadable entries listed but unselectable, and builds one shared resolution/frame-rate choice list for the playlist.
3. User selects **Video (MP4)**, **Audio (MP3)**, **Thumbnail**, **Subtitles**, **Playlist**, or **Batch queue**.
   - Video: select a returned resolution/frame-rate option, read its estimated MP4 size from the list itself, and optionally switch the stream preference between **Best quality** and **Smaller file**, which re-costs every entry; yt-dlp downloads the selected video stream and the best compatible audio, then merges/remuxes to MP4 with FFmpeg.
   - Playlist: choose what each video is saved as (**Video only (MP4)**, **Audio only (MP3)**, or **Subtitles**), select one resolution/frame-rate option (video) or MP3 bitrate (audio) shared by the whole job, then tick the videos to download. Each row shows that video's own size for the shared choice, and a combined estimate covers the current selection. Selected entries are downloaded sequentially with aggregate progress, and an individual failure does not stop later entries.
   - Audio: select 128/192/256/320 kbps and read the estimated MP3 size from the bitrate list, which is costed the same way when duration metadata is available; yt-dlp downloads the best audio and FFmpeg converts it to MP3.
   - Subtitles: select SRT or VTT, a source (author-written first / auto-generated / all tracks), and optionally a single language. No media is saved; one caption file is written per language.
   - Thumbnail: download only the largest thumbnail selected by dimensions/preference.
   - Batch queue: each pasted link is validated, probed, and downloaded in turn, picking its own nearest available quality. Invalid lines and duplicates are reported up front; a failing link is recorded and the queue continues.
4. User presses **Download**. A worker performs the operation outside the Qt event loop, emits strictly time-throttled progress (including unknown-size fragment updates), supports cooperative cancellation between yt-dlp callbacks, and reports success or a categorized, actionable error. FFmpeg's already-started subprocess is not forcibly terminated.
5. The user sees the saved local file path or playlist/queue success-failure summary in the UI, and **Open folder** / **Play** become available for the saved files; logs contain only operational events, error categories, and counters.

### Verifiable goals

- A valid supported URL produces metadata and a non-empty quality list in the background without freezing the UI.
- Every unique available single-video resolution/frame-rate combination is represented once and is selectable.
- Each quality choice reports both what **Best quality** and **Smaller file** would download, and the smaller option is only selectable when a leaner H.264 MP4 exists at the same resolution and frame rate; otherwise the entry is disabled and states why, rather than returning the same file under a different label.
- The **Smaller file** option never re-encodes: no WebM/VP9/AV1 stream is ever selected, so resolution, frame rate, and quality are preserved.
- An explicit playlist probe produces valid video metadata, a shared quality list, and a count of entries skipped during probing.
- A `watch?v=...&list=...` URL is accepted in playlist mode and reduced to its playlist, while the single-video modes still reject it.
- A playlist download uses one shared quality identity or MP3 bitrate, processes only the ticked videos, emits aggregate progress, and continues after an individual item failure.
- Each playlist row reports its own size for the currently selected quality or bitrate, and the combined estimate tracks the ticked subset.
- A subtitle request writes one non-empty `.srt`/`.vtt` file per requested language and saves no media; a video with no caption tracks reports that explicitly.
- A batch queue downloads its links sequentially, reports a per-link outcome for every line, and continues past each failure.
- Aggregate progress for both playlists and batches never moves backwards, even though yt-dlp restarts at 0% for the second file of a merged video-plus-audio download.
- A video or playlist request produces a non-empty MP4 file, or a categorized error if the source cannot be merged/remuxed.
- An audio request at each supported bitrate produces a non-empty MP3 file when FFmpeg is available.
- An audio request embeds the video's cover art in the MP3, leaves no loose image beside it, and still completes when the video has no thumbnail.
- A thumbnail request produces the largest available image and never downloads a video stream.
- Invalid, private, removed, age-restricted, region-locked, network-interrupted, JavaScript-challenge, extractor-changed, missing-FFmpeg, and disk-full cases return actionable messages and leave resumable partial files where yt-dlp supports them.
- Every theme palette passes a contrast check on the text-on-surface pairs the UI actually renders, composited over the surface beneath each role rather than read off the hex values, and every theme's card is fully opaque.
- The theme a user picks is applied on the next launch, and an unreadable, corrupt, or out-of-date settings file leaves the window opening normally on the default theme.
- No theme renders a single clear pixel in the window, and the complete test suite passes in headless mode, including the responsive small-window layout, theme-selector, and frameless-window checks.

**Not in version control**, because all of it is regenerated and a committed copy would go stale against `requirements.txt` and `scripts/`: `.venv/` (`setup.ps1`), `vendor/` (`setup.ps1`, checksum-verified), `dist/` (`build_installer.ps1`), `build/` (PyInstaller scratch), `__pycache__/`, and the twelve `assets/app-*.png` renders. See `.gitignore`, which carries the reason for each.

- `core.engine.Engine` is the only module that knows yt-dlp option details. GUI code receives dataclasses and callbacks, not extractor dictionaries.
- `Engine.probe()` and `Engine.probe_playlist()` are mode-aware metadata entry points. `Engine.download_video()`, `download_audio()`, `download_thumbnail()`, and `download_subtitles()` remain separate single-video operations; `download_playlist()` is the explicit sequential playlist operation and `download_queue()` the batch-queue operation. All of them are also accepted by `Engine.download()`.
- `Engine._output_paths_from_result()` is the one place that reads a completed yt-dlp result, and it checks all three places a path can hide: `requested_downloads` for merged media, `filepath` for a plain download, and `requested_subtitles` for captions, which yt-dlp writes outside the normal download bookkeeping. A caption run therefore returns the complete per-language set with `DownloadResult.path` as its first entry.
- Stream preference is resolved while formats are grouped, not by re-probing: `_build_qualities` computes the best-quality and smallest-MP4 candidate per `(height, fps)` group and attaches the smaller candidate to the winning `VideoQuality` as `smaller_format_id` / `smaller_size_bytes` / `smaller_codec`. A size lookup for a choice with no smaller alternative falls back to the ordinary size, which is what the UI needs.
- Playlist sizing is computed by module-level helpers (`select_playlist_video_quality`, `quality_matches_target`, `playlist_video_size_bytes`, `playlist_audio_size_bytes`, `select_playlist_videos`) so the engine and the GUI derive per-video numbers from one implementation. The engine and the UI therefore never disagree about which quality a video will actually use. `item_slice_progress()` is shared for the same reason: the split of an item's progress slice between reading details and saving media must not drift between the playlist and queue paths.
- Caption language selection lives in `Engine._subtitle_language_options()` and is mirrored by the GUI so the count shown before a run is the number of files that appear afterwards. `MAX_SUBTITLE_LANGUAGES` is the single cap constant, referenced by the engine, the model help text, and the UI.
- All network and filesystem work runs in a worker thread. The GUI only updates widgets from Qt signals.
- Per-video download options use `noplaylist=True`, retries with a jittered backoff, continuation, bounded fragment concurrency, Windows-safe filenames, and no metadata sidecar files. Playlist probing temporarily overrides `noplaylist=False` only for the explicit playlist URL.
- Logging enqueues records away from the UI/download hot path. The rotating destination is `%LOCALAPPDATA%\ClipDock\logs\app.log` with three backups; records contain no submitted URL, local path, title, account data, or raw extractor messages.
- `gui/selectors.SelectorComboBox` is the only combo box type in the window. It exists for two reasons that a plain `QComboBox` cannot satisfy here: the wheel is ignored (a stray scroll must not change the download mode, quality, or theme), and the chevron is painted from the palette because the stylesheet removes the platform arrow. `MainWindow._selector_combos()` collects them from the widget tree rather than from an attribute list, so a combo added later cannot be missed by the theming pass.
- `gui/caption.CaptionButton` is the only caption button type. It paints its own glyph and holds no text at all, because a character in the button's font is laid out against that font's baseline and the three marks then sit at three different heights — which is exactly the "typed label" look it replaced. `CaptionButton.set_caption_colors()` is fed by the same theme pass that feeds the chevrons, because a painted glyph has no text for the stylesheet to colour. The buttons are deliberately undecorated: flat, unrounded, no resting fill, full caption height, flush to the top-right corner. What makes a window frame legible is that it looks the same in every application.
- The caption strip is a sibling **above** the scroll area, not a row inside the scrolling card. Inside it, the scroll bar ran the full window height beside the window buttons and the caption scrolled out of sight; a caption is fixed furniture and a scroll bar belongs to the content it scrolls. The strip therefore paints the card's own colour, since it is now the only thing painting the top of the window.
- Rounded window corners come from `DwmSetWindowAttribute(DWMWA_WINDOW_CORNER_PREFERENCE)` plus `DWMWA_BORDER_COLOR`, applied from `showEvent` once a native handle exists. This is deliberate: a Qt translucency approach (`WA_TranslucentBackground`) would break the opaque-card guarantee that `gui/themes.py` and the rendered-pixel test both depend on. On Windows builds without those attributes the calls fail harmlessly and the window stays square.
- The scroll bar handle's inset comes from its **own** margin, never from the bar's margin. Qt honours a handle margin and does not fill a scroll bar's margin with the bar's background, so a margin on the bar is a clear stripe down the edge of the window. The radius is set to exactly half the handle's width so both ends are round; an arbitrary radius produces a rounded rectangle with square top and bottom, which is the thing that reads as stock.
- `PlaylistDownloadResult.failed_video_ids` carries the ids of videos the engine could not save, separately from the `(title, message)` failure tuples. Retry is wired to the ids, so a playlist holding the same title twice still retries the right video; the failure tuples alone do not identify a video.
- Dependency locations are resolved from an ordered list of roots — the frozen executable's own directory, the PyInstaller bundle directory (`sys._MEIPASS`), then the source root — followed by an explicit environment override and `PATH`. This is what lets the packaged `.exe` find the `vendor/` folder sitting next to it. Missing FFmpeg is reported before a media operation that needs it.

## [DECISIONS_LOG]

- **2026-09-25 — Windows-only:** avoids unsupported platform paths and packaging branches.
- **2026-09-25 — PySide6:** selected over PyQt for its LGPL-oriented distribution model.
- **2026-09-25 — Python module API for yt-dlp:** the pinned wheel is the extraction engine; the pinned standalone executable is also fetched for the Windows distribution bundle and diagnostics.
- **2026-09-25 — Single video by default:** the normal video/audio/thumbnail modes use `noplaylist=True` and reject collection links, preserving the original single-video scope.
- **2026-09-25 — Explicit sequential playlist mode:** the user must select **Playlist** and provide an explicit `/playlist?list=...` URL; one `(height, fps)` choice is applied to every valid entry, downloads run sequentially, aggregate progress is emitted, and per-video failures do not stop later entries.
- **2026-09-25 — Per-video playlist selection:** the playlist job carries an optional `selected_video_ids` tuple (`None` = all videos, preserving the previous behavior for non-UI callers). Selection is keyed by the stable YouTube video id, and `select_playlist_videos()` preserves playlist order regardless of the order the user ticked rows. Downloading an empty selection raises `DownloadFailure(code="no_selection")` rather than silently succeeding with nothing.
- **2026-09-25 — Playlist video or audio:** `PlaylistMedia` (VIDEO/AUDIO) extends the playlist request. Audio downloads reuse `download_audio()` with one shared bitrate, validated against `SUPPORTED_PLAYLIST_AUDIO_BITRATES`. This is a narrow extension of the explicit playlist mode, not a new batch subsystem.
- **2026-09-25 — Unavailable entries stay visible:** a playlist entry that is private, removed, live-only, or has no usable stream is returned as `VideoInfo(selectable=False, unavailable_reason=...)` instead of being dropped. It appears in the list with its reason, cannot be ticked, and is excluded from both the quality aggregation and the download, so users can see what they are missing. `PlaylistInfo.video_count` still reflects usable entries, and `skipped_count` retains its original meaning for entries that could not be described at all.
- **2026-09-25 — Per-video size estimates:** each playlist row shows the size that specific video will actually produce under the shared choice, using the same selection helper the download uses, so the displayed fallback size matches the fallback that is downloaded. Tooltips state whether the row is an exact match or a nearby fallback. The combined estimate is summed over ticked rows only and reports how many selected rows lack metadata rather than guessing (superseded below: the standalone totals are gone, and the per-row size in the table is the only number shown).
- **2026-09-25 — Quality identity:** quality choices are unique `(height, fps)` variants; the best available format for each variant is selected and merged with best audio when needed. Playlist entries use the nearest available identity when the selected variant is not present.
- **2026-09-25 — MP4/MP3 guarantees:** FFmpeg is mandatory for video merge/remux and audio conversion; failure to produce the requested container is surfaced rather than silently returning another format.
- **2026-09-25 — Largest thumbnail:** thumbnails are ranked by pixel area, then explicit preference, then URL-independent stable order; no size selector is exposed.
- **2026-09-25 — No account or DRM bypass:** private, age-restricted, region-locked, and DRM-protected content fails clearly; the application does not request cookies or circumvent access controls.
- **2026-09-25 — No EJS/JavaScript runtime added:** the approved dependency set contains only PySide6, yt-dlp, and FFmpeg. The current yt-dlp extractor can require `yt-dlp-ejs` plus a JavaScript runtime for some YouTube videos; this app reports that condition clearly rather than silently adding an unapproved dependency. The user approved retaining the current set, so this is an intentional coverage limitation rather than an open implementation task.
- **2026-09-25 — LGPL FFmpeg encoder:** the verified Windows LGPL build does not include `libx264`; MP4 conversion therefore uses its available `libopenh264` encoder with AAC audio, and the real fixture/live-video checks verify the resulting H.264/AAC MP4.
- **2026-09-25 — User responsibility:** the README retains the documentation-only guidance to comply with applicable law, copyright rules, and YouTube terms; the former notice is not displayed in the application window.
- **2026-09-25 — Explicit UI themes:** light and dark palettes define text, surfaces, borders, controls, progress, tooltips, and disabled states explicitly rather than relying on the Windows system palette. The **Theme** word is rendered as a distinct badge beside the selector, the selector remains available while a worker is running, and the switch is covered by a headless theme test.
- **2026-09-25 — Fixed-size theme control:** the theme label and selector are laid out horizontally inside a `QSizePolicy.Fixed` container, so the group keeps a constant width at every window size. The previous stacked layout let the badge absorb the window's spare width, which made "Theme" grow to fill a maximized or full-screen window. Verified at 760x540, 860x700, 1600x900, and 2560x1440.
- **2026-09-25 — Executable via PyInstaller:** `scripts/build_exe.ps1` produces `dist\ClipDock\ClipDock.exe`, a double-clickable program that needs no separate Python install. PyInstaller is build-time only and never enters `requirements.txt`, so the approved runtime dependency set is unchanged. The one-folder layout is the default because bundling ~145 MB of vendor binaries into a single `.exe` means re-extracting it to a temp directory on every launch; `-OneFile` is available when a single file is preferred. The bundled `vendor/` binaries are copied next to the executable, which is why binary discovery now checks the frozen executable's directory before the PyInstaller bundle directory.
- **2026-09-25 — Separate dist folders:** the source distribution builds to `dist\YouTubeDownloader-source` and the executable to `dist\ClipDock`. Both scripts delete their target folder before rebuilding, so distinct names are what stops one build from destroying the other's output. The source distribution keeps its old folder name: it is a name, not a product, and renaming it would delete a build the user may still want.
- **2026-09-25 — Generated application icon:** `tools/make_icon.py` renders the icon with Qt and writes a Windows `.ico` containing PNG entries from 16 to 256 px, so the packaged executable, taskbar entry, and shortcuts all carry an icon without a binary asset being hand-committed.
- **2026-09-25 — Packaged self-check:** `app.py --check` builds the real window and resolves FFmpeg, then exits 0 or 1. `build_exe.ps1` runs it against the freshly built executable so a broken bundle fails the build instead of shipping a program that cannot start. The result is written to the rotating log because a windowed executable has no console.
- **2026-09-26 — `ffprobe` dropped from the bundle:** the application only ever calls `require_ffmpeg`; `find_ffprobe` existed solely to satisfy the self-check. `ffprobe.exe` is 128 MB — a third of the whole build — and is never invoked, so `tools/fetch_dependencies.py` now extracts only `ffmpeg.exe` and deletes any previously installed copy. This is safe because yt-dlp treats ffprobe as optional and already falls back to parsing `ffmpeg -i` output in `FFmpegPostProcessor.get_audio_codec`; only the metadata postprocessor requires it, which this app never uses. The media tests read codecs and bitrate out of `ffmpeg -i` rather than probing, so they keep full coverage. Net effect: the executable folder drops from ~407 MB to ~279 MB with no feature loss.
- **2026-09-26 — Pre-download size estimates:** quality choices use YouTube `filesize`/`filesize_approx` metadata and add the best compatible audio estimate when a video-only stream is selected; missing metadata is shown as unavailable rather than guessed silently.
- **2026-09-25 — Smooth progress:** yt-dlp chunk callbacks are coalesced to a strict time-based rate, including indeterminate fragment callbacks, so the GUI event loop is not flooded and the displayed value does not jump backward during retries.
- **2026-09-25 — UI notice removal:** the former responsibility sentence was removed from the application window at the user's request; the README retains the separate documentation-only responsibility guidance.
- **2026-09-26 — `watch?v=…&list=…` accepted in playlist mode:** any accepted YouTube URL that carries a `list=` parameter is rewritten to `https://www.youtube.com/playlist?list=<id>`, with the host normalized to `www.youtube.com`. Non-YouTube and collection URLs, and links with no `list`, are still rejected. The single-video modes keep rejecting collection links, which is the gap the batch queue fills.
- **2026-09-26 — Per-resolution stream preference:** `StreamPreference` (QUALITY / SMALLER_FILE) rides on `VideoQuality`, `PlaylistQuality`, and the three request types. `SMALLER_FILE` only ever offers an MP4 stream that is already H.264 (`_is_mp4_h264`), because the app always writes MP4 and YouTube's smaller VP9/AV1 streams are WebM — offering one would mean a re-encode. This is a deliberate quality-preservation guarantee, not an oversight: resolution, frame rate, and picture are untouched, and there is no transcode. The alternative candidates are attached to each quality while formats are being grouped, so no second probe is needed. The UI gates the choice on `has_smaller_alternative` (per video) or `smaller_video_count` (per playlist) and disables the entry with an explanation when there is nothing to switch to, since a greyed-out choice that still returned the same file would be worse than no choice. A batch queue is exempt because no link is probed until it is reached. Verified live: 1080p 122.3 MB → 80.5 MB, 480p 25.2 MB → 16.7 MB and 720p 35.0 MB → 28.5 MB on one video; 1080p60 571.3 MB → 255.5 MB and 720p60 354.5 MB → 153.3 MB on another. The 1440p, 2160p, and lowest-fps entries correctly offer nothing because their small streams are WebM.
- **2026-09-26 — Subtitles as a first-class output:** `DownloadMode.SUBTITLES` and `SubtitleFormat` (SRT/VTT) sit alongside MP4/MP3/thumbnail. `SubtitleSource` selects PREFERRED (author-written, falling back to ASR), AUTOMATIC (ASR only), or ALL. A caption run uses `skip_download=True` with empty post-processors, so no media is saved. `AUTOMATIC` must set `writesubtitles=False`, because yt-dlp hands back the author-written track whenever `writesubtitles` is on — without that, "auto-generated" would silently return the human track. `PlaylistMedia.SUBTITLES` extends playlists, skipping caption-less entries with a stated reason.
- **2026-09-26 — Caption language cap of 25:** YouTube advertises 160+ tracks on most videos, and all but the original language are server-side machine translations that the timedtext endpoint serves far more reluctantly — an uncapped run is refused partway through with HTTP 429. Every branch that derives codes from the advertised list is therefore capped at `MAX_SUBTITLE_LANGUAGES`, and the GUI reports the same capped count before the run so the two can never disagree. A language the user picked by hand is never capped. Multi-language runs are paced with `sleep_interval_subtitles`, and the shared HTTP retry gained a jittered exponential backoff because yt-dlp's default 10 retries fire back-to-back and cannot outlast a rate limit.
- **2026-09-26 — Partial caption runs are a success:** if YouTube stops answering after some files are written, the engine reports those files with a warning rather than presenting the whole run as a failure and discarding the work. The rescue scans the output folder by name for `[<video id>]` rather than globbing, because `[` and `]` are glob metacharacters and would not match themselves. A run that wrote nothing is still a failure.
- **2026-09-26 — Batch queue:** a new `DownloadMode.QUEUE` runs any number of pasted links one after another, continuing past each failure and reporting a per-link outcome. It reuses the playlist machinery with a `PlaylistQuality` target so each link picks its own nearest available resolution, since links in a batch come from unrelated channels. `_QUEUE_SUPPORTED_MODES` is VIDEO/AUDIO/THUMBNAIL/SUBTITLES; playlist and queue never nest. There is no upfront probe, so there is no total-size estimate — a live per-link status table is more honest than a number that would have to be re-probed for every link. Invalid lines and duplicates are counted and reported up front.
- **2026-09-26 — Open folder and Play:** after any download finishes, the saved paths are remembered and two buttons become available, using `QDesktopServices` to reveal the output folder and to hand the file to the default player. Multi-file results (a playlist, a caption set) act on the folder; a single media or audio file can be played directly.
- **2026-09-26 — 14 explicit themes (superseded below):** the palette catalog moved into `gui/themes.py` and covered the popular schemes including Glass, Transparent, VS Code Dark+, and One Dark. - **2026-10-01 — Icon redrawn as a nested download arrowhead, on flat graphite:** the clip-into-a-dock mark was rejected as reading like a scam program rather than a video downloader, and three rounds of candidates followed. PyInstaller's own `FixedFileInfo.__init__` takes `OS`, `fileType`, `subtype` and `date`, so the build would have failed with `unexpected keyword argument`. **Ten of the eleven new tests pass over that broken file**, which is the finding: the file's syntax is valid Python, the values are right, and it is still unusable. The one test that catches it is `test_pyinstaller_itself_can_read_the_generated_resource`, which loads the file with `load_version_info_from_text_file` — PyInstaller's own parser, the one the build uses — rather than with anything written here.

  **`ast.literal_eval` cannot do that job, and its refusal is correct.** `VSVersionInfo(...)` is a *call*, and `literal_eval` rejects calls by design; the first three verification attempts failed on this, `ast.literal_eval`, then a nonexistent `exec_versionfile`, then attribute names (`StringStruct.name`/`.val`, and `FixedFileInfo.fileVersionMS`/`.LS` rather than the constructor's keywords) that were assumed rather than read. A substitute parser would have accepted the broken file happily. Every remaining check was then confirmed to fail against the defect it claims to catch: reverting the keys fails exactly one test, typing a literal `version = "0.2.0"` into `render()` fails two, and generating the file after `$arguments = @(` fails three.

  The resource is written with no BOM because PyInstaller evaluates the file as UTF-8 and `Out-File -Encoding utf8` on Windows PowerShell 5.1 emits one — a syntax error rather than something tolerated. `FileVersion` and `ProductVersion` carry `__version__` as text, and `filevers`/`prodvers` carry it padded to four integers, padded rather than rejected because `0.10.0` must not read as older than `0.9.0` and because Task Manager's Details tab and most log parsers read the numbers, not the strings.

  **`--check` is wired into the release pass, by decision.** It writes nothing and exits non-zero when the file on disk differs from what `__version__` would produce. Left unwired it was close to dead code — its only exercise was its own test — and the user chose to give it the verification round in step 10 instead of having it deleted. **What it will actually check there, and what it will not, is worth stating now rather than discovering later:** re-running it immediately after `build_exe.ps1` wrote the file is circular, because the same call produced both sides. Its real use is *after* something else could have touched the file — a second build, a merge, a stray editor — and the authoritative check in that round is still reading the version back off the rebuilt `ClipDock.exe`, which asks the artefact rather than the generator. `--check` is the cheap guard in front of that, not a substitute for it.

  **The defect, measured against the shipped 0.2.0 files rather than described.** `read_version_info_from_executable` on the installed `%LOCALAPPDATA%\Programs\ClipDock\ClipDock.exe` does not return an empty result — it **raises** `pywintypes.error (1813, 'EnumResourceNamesW', 'The specified resource type cannot be found in the image file')`, because there is no `RT_VERSION` resource in the image at all. The same call on `dist\ClipDock-Setup.exe` returns `FileVersion 0.2.0.0`, `ProductName "ClipDock Setup"`, `FileDescription "ClipDock Setup"`, and `Comments "This installation was built with Inno Setup."` So the asymmetry is exact: **the installer names a version and the program it installs names none.**

  **That raise is the project's recurring lesson in a sixth shape, and it nearly became a seventh false pass.** The natural guard is `if not info: report a missing resource`, and on this reader it is **unreachable** — the exception fires first, so a check written that way would pass on a broken executable by never entering its own failure branch. A reader that returns a falsy value when a resource is missing makes that mistake impossible; this one does not. Anything in the release pass that reads a version off an executable has to catch the exception, and the only safe reading of "no exception" is still "verify the numbers", because a *present but wrong* resource raises nothing at all.

The engine builds `outtmpl` as `str(output_dir / CLEAN_OUTTMPL)` (`engine.py:350`), which is absolute even though `CLEAN_OUTTMPL` itself (`"%(title).180B.%(ext)s"`) is relative — so `paths` is inert for **every** download, media and captions alike. An interrupted Sprite Fright download left **no `.parts` directory at all**; `rglob` over the output directory found the fragments beside the target instead: `Sprite Fright - Blender Open Movie.f620.mp4.part`, `.part-Frag3.part` (2,876,642 B), `.part-Frag10.part`, and a 69-byte `.f620.mp4.ytdl`.  `unfinished_downloads()` (`engine.py`) finds those pieces where they actually are and reports each interrupted download as an `UnfinishedDownload` naming the file it will become. It **deliberately does not look in `.parts`**, because measurement showed no such directory exists, and a test pins that so the false premise cannot creep back. The target name is recovered by stripping the marker suffix and never by rebuilding the output template - repeating the template's rules here is how a clean filename silently stopped being recognised once already. Nothing here opens or deletes a piece: an interrupted run's `.part` can still be **locked** (`PermissionError: [WinError 32]` on cleanup) while the process lives, so the folder is only listed and every size is read defensively, reporting **None rather than half a sum** when a piece cannot be measured. A lone 69-byte `.ytdl` is exposed through `has_fragments = False`, because it is evidence that a run started, not that there is anything to continue from. **The interactive half is built, paired with Pause (2026-10-07)** - which is what this entry asked for: a standalone Resume would have to reconstruct the request for a download the app no longer holds, so Resume is bound to the job *this session* stopped and re-runs the stored request rather than whatever is on screen now. Whether resume nonetheless *works* is **not established**: the second identical run opened at 0.00% and re-fetched fragments that run 1 had already written (Frag3 went 2,876,642 → 1,047,552 B), which reads as a restart, but the progress hook reports 0 before the first fragment completes regardless, so that is suggestive rather than decisive and must not be recorded as a proven restart. Separately, cancelling left the `.part` file **locked** (`PermissionError: [WinError 32]` on cleanup) while the process lived, which in a long-running app is the user's own retry or delete being refused; that is a resource-handle question worth its own entry. **Pause and Resume ship.** `main_window.py:2872` `_pause_job` stops the running download through the same `controller.cancel()` Cancel uses and records that a pause did it, because both stops reach `_on_job_cancelled` as an identical cancellation and only the intent separates them - unrecorded, Cancel would offer to continue a job the person had just refused. `main_window.py:2920` `_refresh_resume_button` shows Resume **only when it can act**: a stopped request exists, the destination holds part-written files *with real bytes* (`has_fragments`), and those pieces differ from a fingerprint of the folder taken **before the job began**, so an earlier session's crash in the same folder is not offered as though this job had produced it. The button is hidden rather than greyed out, which is stricter than Retry and is the point of the control; a tooltip counts exactly what it will continue. Six GUI tests pin all of it and all six mutations of it were caught - dropping the recorded request, the snapshot comparison, the `has_fragments` filter, the pause/cancel distinction, the `_pauseable` gate that keeps a probe from being pausable, or the enabling line itself. Pause's own tooltip asserts it is **not** a true pause, because yt-dlp exposes no pause primitive and this is a graceful stop that keeps the pieces. **What is still missing is the restart half of this entry's title.** Nothing reconstructs a request once the program is closed: `settings.json` remembers a theme and a checkbox, and its own docstring says so - *the application has exactly one thing worth remembering between runs* - while a `.part` file carries no link. So Resume is a this-session control: after a restart `unfinished_downloads()` still finds the pieces and nothing can continue them, because continuing needs the request. Making that work needs either a persisted resume record, which puts URLs on disk and contradicts the settings file's stated design, or the job records the History feature will write - a decision not yet taken, and the reason this box stays unticked alongside the still-unverified question of whether a continuation resumes rather than restarts. **The trigger is decided and built: the `.part`/`.part-Frag*`/`.ytdl` files beside the target**, with `paths` left alone — making it effective would mean rebuilding `outtmpl` as a relative path, which is a change to every filename the app has ever written, in exchange for tidier temporary files. The interactive half is unaffected by that choice.
- [ ] **An automatic update check on startup, announced quietly.** The check is manual today, from the Help menu, and deliberately so - `main_window.py:354` records that answering in seconds would be worse than not checking at all. Everything needed already exists: `check_for_updates()`, the report-only guarantee that it never installs, and the `RELEASES_URL` fallback. What is new is the timing, and the timing is the whole feature: run it after the window is up and idle rather than during startup, say **nothing at all** when the current version is the latest, show a dismissible corner toast when one is not, remember that it has already run today so it cannot nag on every launch, and offer a setting to turn it off. One constraint is load-bearing and comes straight from the 0.2.0 release: the banner must never imply urgency it has not got. `core/updates.py:32` pins `/releases/latest`, which excludes pre-releases, so only a genuinely published release can ever be announced - a pre-release must stay invisible, because announcing one would tell every current user they were up to date when they are not.
- [ ] **A "start with Windows" option on the installer, checked by default (decided 2026-10-03).** Small, contained, and the mechanism is half present: `clipdock.iss` already has a `desktopicon` task pattern and a `[Icons]` section that creates the Start Menu entry, and `PrivilegesRequired=lowest` means a `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` entry needs no administrator rights at all. It wants a new **checked-by-default** task - the user's decision, against a recommendation to default it off - plus the `Run` value it writes, and - the part that is easy to forget and leaves a mess - **removal of both on uninstall**, or the machine is left holding an autostart entry pointing at an executable that no longer exists. Two consequences of defaulting it on, which is why the reasoning is written down rather than left implicit. **The label has to say what it does**: a checked box on the installer's first page is consent to launch a GUI application on every sign-in, and "Start with Windows" does not convey that a frameless app window will appear unprompted. And because it is on by default it will be the common case, so the uninstall path is not a corner case to be tested once - it is the case that has to be right. The option must stay **visible and un-ticked-able** in the same `[Tasks]` section as `desktopicon`, so a user who does not want it can untick it during the same install rather than hunting through Windows startup settings afterwards. **Built 2026-10-07, still unticked on purpose.** The `autostart` task sits on the same Select Additional Tasks page as `desktopicon`, with no `unchecked` flag - a [Tasks] entry is checked unless that flag says otherwise, so the *absence* of it is the whole of "checked by default" - and with no `checkedonce` either, because that flag un-ticks the box whenever Inno finds a previous version, which would quietly switch the option off for everyone on their first upgrade. It writes `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`, quoted, because the install path contains a space and Windows reads an unquoted Run value as the first token plus everything after it. The value is removed in **both** directions: `uninsdeletevalue` so uninstall does not leave a sign-in entry pointing at an executable that has been deleted, and a `ValueType: none; Flags: deletevalue; Tasks: not autostart` entry, because Inno only creates what is selected and never retracts what an earlier install created - without that second one, unticking the box during an upgrade would have had no effect at all. Six installer tests pin it, and the script compiles under ISCC 6. **What it has not had is a real install-and-uninstall cycle**: "the value appears, and then it goes away" is a claim only running the installer can make, so this box stays open until the release pass does exactly that.
